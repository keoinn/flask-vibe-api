# 個人記帳本 API 資料交換格式規格書 (Data Exchange Specification)

本文件依據講義《從資料表到 Flask API》步驟 14 之約定撰寫，統整個人記帳本後端 RESTful API 之請求與回應交換規格，供前端工程師介接使用。

---

## 一、共通規則 (Common Rules)

1. **回應外層封裝**：
   每一筆 HTTP 回應正文固定只包含以下三個 JSON 鍵，不多不少：
   - `code`（整數）：與 HTTP 狀態碼完全相同的數值。
   - `message`（字串）：給使用者閱讀的人話說明。
   - `data`（物件 / 陣列 / null）：成功時存放處理結果；失敗時恆為 `null`。

   ```json
   {
     "code": 200,
     "message": "查詢成功",
     "data": []
   }
   ```

2. **HTTP 狀態碼與回應對照**：
   | 情況 | HTTP 狀態碼與 `code` | `data` 內容 |
   | :--- | :--- | :--- |
   | 查詢成功（含空清單） | `200` | 目標物件或陣列（空清單為 `[]`） |
   | 新增成功 | `201` | 資料庫寫入後之完整列物件（含新生主鍵與時間戳記） |
   | 更新成功、餘額、持有、對獎、月合計 | `200` | 該端點約定之專屬物件 |
   | 格式錯誤、驗證未過、違反商業約束 | `400` | `null` |
   | 指定的主鍵或路徑不存在 | `404` | `null` |
   | 資料庫連線失敗或未處理例外 | `500` | `null` |

3. **客戶端禁止傳送的欄位**：
   - 客戶端在發送 `POST` 或 `PATCH` 請求時，**不得**包含 `id`、`created_at`、`updated_at`。即便送出，後端亦不採用。
   - 發票資源中，發票號碼 `number` 建立後不可更改，`PATCH` 請求禁止帶入 `number`。

4. **資料型別與編碼慣例**：
   - **日期**：一律使用 ISO 8601 格式字串 `YYYY-MM-DD`（例如 `"2026-11-01"`）。
   - **時間戳記**：`created_at`、`updated_at`、`voided_at` 使用 UTC 國際標準 ISO 8601 字串（例如 `"2026-11-01T00:00:00Z"`）。
   - **數值欄位**：金額（`amount`、`line_amount`、`cash_amount`）、匯率（`fx_rate_to_twd`）、股數（`quantity`）、單價（`price`）、手續費（`fee`）、稅額（`tax`）、比例（`ratio`）一律為 JSON 數字型別，不包裝為字串。
   - **幣別**：一律為 ISO 4217 標準 3 碼大寫英文字串（例如 `"TWD"`、`"USD"`、`"JPY"`）。

5. **可空欄位（Nullable Fields）表現方式**：
   - 在回應 JSON 中，定義為可空的欄位若無數值，**必須明確以 `null` 出現**，不得省略鍵名。
   - 在發送請求時，客戶端可傳送 `null` 或直接省略該鍵，兩者效果完全相同。

## 二、失敗回應範例 (Error Responses)

失敗時 `data` 恆為 `null`，`message` 採用固定的人話句子。回應正文中**絕對不含**資料庫表名、約束名、SQL 語法、SQLSTATE 或程式例外堆疊。

### 1. HTTP 400（客戶端錯誤 / 違反約束）
以「帳戶名稱重複」為例：
```json
{
  "code": 400,
  "message": "這個名稱已經有了",
  "data": null
}
```

### 2. HTTP 404（資源不存在）
以「查詢不存在之帳戶 ID」為例：
```json
{
  "code": 404,
  "message": "找不到這一筆",
  "data": null
}
```

## 三、查詢參數規格 (Query Parameters)

清單查詢端點支援以下 URL 查詢字串參數，查詢參數均為選填（月合計 `month` 為必填）：

| 端點 | 參數名稱 | 型別 / 格式 | 說明 |
| :--- | :--- | :--- | :--- |
| `GET /api/incomes` | `account_id` | 整數 | 依帳戶 ID 篩選入帳 |
| | `category_id` | 整數 | 依入帳分類 ID 篩選入帳 |
| | `date_from` | `YYYY-MM-DD` | 篩選入帳日（`received_on`）起始範圍（含） |
| | `date_to` | `YYYY-MM-DD` | 篩選入帳日（`received_on`）結束範圍（含） |
| `GET /api/expenses` | `account_id` | 整數 | 依帳戶 ID 篩選花費 |
| | `category_id` | 整數 | 依花費分類 ID 篩選花費 |
| | `invoice_id` | 整數 | 依掛載之發票 ID 篩選花費 |
| | `date_from` | `YYYY-MM-DD` | 篩選消費日（`spent_on`）起始範圍（含） |
| | `date_to` | `YYYY-MM-DD` | 篩選消費日（`spent_on`）結束範圍（含） |
| `GET /api/invoices` | `period_key` | `YYYY-MM` | 依統一發票期別篩選（如 `2026-01`） |
| | `prize_status` | 字串 | 依對獎狀態篩選：`unchecked`、`lost`、`won`、`claimed`、`void` |
| `GET /api/trades` | `instrument_id` | 整數 | 依投資標的 ID 篩選交易 |
| | `account_id` | 整數 | 依關聯交割帳戶 ID 篩選交易 |
| `GET /api/summary` | `month` | `YYYY-MM` | **【必填】** 指定查詢月份（如 `2026-08`） |

## 四、各資源回應物件與範例 (Resource Schema & Examples)

> 註：以下範例中的 `id` 與關聯外鍵統一以數字 `1` 起算展示，實際呼叫時請以伺服器回傳之真實 ID 為準。

### 1. 健康檢查 (Health Check)
- **路徑**：`GET /api/health`
- **成功回應範例**：
  ```json
  {
    "code": 200,
    "message": "伺服器運行正常",
    "data": {
      "status": "ok",
      "time": "2026-11-13T04:15:00Z"
    }
  }
  ```
- **欄位說明**：
  | 欄位名稱 | 型別 | 可空 | 說明 |
  | :--- | :--- | :--- | :--- |
  | `status` | 字串 | 否 | 伺服器運作狀態，固定為 `"ok"` |
  | `time` | 字串 | 否 | 伺服器目前時間（UTC ISO 8601） |

---

### 2. 帳戶 (Accounts)
- **對應資料**：講義 Postman 測試資料「現金錢包」
- **成功回應範例**（`POST /api/accounts` 或 `GET /api/accounts/1`）：
  ```json
  {
    "code": 201,
    "message": "新增帳戶成功",
    "data": {
      "id": 1,
      "name": "現金錢包",
      "kind": "cash",
      "currency": "TWD",
      "opening_balance": 1000.0,
      "statement_day": null,
      "payment_day": null,
      "created_at": "2026-11-01T00:00:00Z",
      "updated_at": "2026-11-01T00:00:00Z"
    }
  }
  ```
- **欄位說明**：
  | 欄位名稱 | 型別 | 可空 | 說明 |
  | :--- | :--- | :--- | :--- |
  | `id` | 整數 | 否 | 帳戶唯一主鍵 |
  | `name` | 字串 | 否 | 帳戶名稱（全系統唯一） |
  | `kind` | 字串 | 否 | 帳戶類型：`cash`、`bank`、`credit_card`、`broker` |
  | `currency` | 字串 | 否 | 帳戶預設幣別（3 碼，如 `"TWD"`） |
  | `opening_balance` | 數字 | 否 | 開帳餘額（預設 `0.0`） |
  | `statement_day` | 整數 | 是 | 信用卡結帳日（1～31） |
  | `payment_day` | 整數 | 是 | 信用卡繳款日（1～31） |
  | `created_at` | 字串 | 否 | 建立時間（UTC ISO 8601） |
  | `updated_at` | 字串 | 否 | 更新時間（UTC ISO 8601） |

---

### 3. 帳戶餘額 (Balance)
- **對應端點**：`GET /api/accounts/1/balance`
- **成功回應範例**（步驟 14 約定格式）：
  ```json
  {
    "code": 200,
    "message": "取得帳戶餘額成功",
    "data": {
      "account_id": 1,
      "currency": "TWD",
      "currency_balance": 800.0,
      "twd_balance": 800.0
    }
  }
  ```
- **欄位說明**：
  | 欄位名稱 | 型別 | 可空 | 說明 |
  | :--- | :--- | :--- | :--- |
  | `account_id` | 整數 | 否 | 帳戶主鍵 |
  | `currency` | 字串 | 否 | 帳戶原幣別代碼 |
  | `currency_balance` | 數字 | 否 | 帳戶原幣別即時餘額（開帳 + 轉入 - 轉出 + 入帳 - 花費 + 投資交割） |
  | `twd_balance` | 數字 | 否 | 折算為新台幣之即時餘額 |

---

### 4. 移轉 (Transfers)
- **對應資料**：講義 Postman 測試資料「轉帳 200」（自現金錢包轉存銀行）
- **成功回應範例**（`POST /api/transfers`）：
  ```json
  {
    "code": 201,
    "message": "新增移轉成功",
    "data": {
      "id": 1,
      "transferred_on": "2026-11-03",
      "amount": 200.0,
      "currency": "TWD",
      "fx_rate_to_twd": 1.0,
      "from_account_id": 1,
      "to_account_id": 2,
      "note": "轉存銀行",
      "created_at": "2026-11-03T10:00:00Z",
      "updated_at": "2026-11-03T10:00:00Z"
    }
  }
  ```
- **欄位說明**：
  | 欄位名稱 | 型別 | 可空 | 說明 |
  | :--- | :--- | :--- | :--- |
  | `id` | 整數 | 否 | 移轉唯一主鍵 |
  | `transferred_on` | 字串 | 否 | 移轉日期（`YYYY-MM-DD`） |
  | `amount` | 數字 | 否 | 移轉金額（大於 0） |
  | `currency` | 字串 | 否 | 移轉幣別代碼 |
  | `fx_rate_to_twd` | 數字 | 否 | 換算新台幣匯率（大於 0） |
  | `from_account_id` | 整數 | 否 | 轉出帳戶 ID |
  | `to_account_id` | 整數 | 否 | 轉入帳戶 ID（不可與轉出帳戶相同） |
  | `note` | 字串 | 是 | 備註說明 |
  | `created_at` | 字串 | 否 | 建立時間（UTC ISO 8601） |
  | `updated_at` | 字串 | 否 | 更新時間（UTC ISO 8601） |

  | :--- | :--- | :--- | :--- |
  | `id` | 整數 | 否 | 分類唯一主鍵 |

  | `description` | 字串 | 是 | 分類說明描述 |

### 6. 入帳 (Incomes)
- **對應資料**：講義 Postman 測試資料「十一月薪水 500」
- **成功回應範例**（`POST /api/incomes` 或 `GET /api/incomes/1`）：
  ```json
  {
    "code": 201,
    "message": "新增入帳成功",
    "data": {
      "id": 1,
      "received_on": "2026-11-01",
      "amount": 500.0,
      "currency": "TWD",
      "fx_rate_to_twd": 1.0,
      "category_id": 1,
      "account_id": 2,
      "source": "十一月薪水",
      "note": null,
      "invoice_id": null,
      "trade_id": null,
      "created_at": "2026-11-01T08:00:00Z",
      "updated_at": "2026-11-01T08:00:00Z"
    }
  }
  ```
- **欄位說明**：
  | 欄位名稱 | 型別 | 可空 | 說明 |
  | :--- | :--- | :--- | :--- |
  | `id` | 整數 | 否 | 入帳唯一主鍵 |
  | `received_on` | 字串 | 否 | 入帳日期（`YYYY-MM-DD`） |
  | `amount` | 數字 | 否 | 入帳金額（大於 0） |
  | `currency` | 字串 | 否 | 幣別代碼（預設 `"TWD"`） |
  | `fx_rate_to_twd` | 數字 | 否 | 換算新台幣匯率（大於 0） |
  | `category_id` | 整數 | 否 | 參照之入帳分類 ID |
  | `account_id` | 整數 | 否 | 存入之帳戶 ID |
  | `source` | 字串 | 是 | 來源說明（與 `note` 不得同時為空） |
  | `note` | 字串 | 是 | 備註說明（與 `source` 不得同時為空） |
  | `invoice_id` | 整數 | 是 | 若為發票中獎，指向 `invoices.id`（全表唯一） |
  | `trade_id` | 整數 | 是 | 若為股利或減資款項，指向 `trades.id`（全表唯一） |
  | `created_at` | 字串 | 否 | 建立時間（UTC ISO 8601） |
  | `updated_at` | 字串 | 否 | 更新時間（UTC ISO 8601） |

  | `created_at` | 字串 | 否 | 建立時間（UTC ISO 8601） |
  | `updated_at` | 字串 | 否 | 更新時間（UTC ISO 8601） |

## 五、內部錯誤與伺服器日誌 (Internal Errors & Server Logging)

當 API 呼叫失敗時，前端用戶端只會取得簡潔的 HTTP 狀態碼與固定人話句子。伺服器底層的詳細錯誤資訊（包含資料庫約束名稱、原始 SQL 語句、例外類別與除錯細節）**嚴禁暴露給用戶端**，僅結構化輸出並保存在伺服器內部日誌中。

### 1. 伺服器內部日誌結構
日誌物件包含以下標準鍵：

| 鍵 | 型別 | 說明 |
| :--- | :--- | :--- |
| `time` | 字串 | 發生時間（UTC ISO 8601 格式） |
| `request_id` | 字串 | 本次請求的唯一追蹤識別碼（由伺服器生成） |
| `method` | 字串 | HTTP 請求方法（如 `POST`、`GET`） |
| `path` | 字串 | 請求端點路徑（不含敏感查詢參數） |
| `http_code` | 整數 | 回應給客戶端的 HTTP 狀態碼（如 400, 404, 500） |
| `error_code` | 字串 | 內部標準錯誤代碼（見下表） |
| `exception_type`| 字串 | 例外類別名稱（若無則為 `null`） |
| `sqlstate` | 字串 | PostgreSQL 5 碼 SQLSTATE 錯誤代碼（非 DB 錯誤為 `null`） |
| `constraint_name` | 字串 | 違反的資料庫約束名稱（若無則為 `null`） |
| `table_name` | 字串 | 涉及的資料表名稱（若無則為 `null`） |
| `detail` | 字串 | 資料庫驅動程式或核心邏輯之原始錯誤說明 |

> **重要規範**：上述所有鍵名僅於伺服器記錄日誌時使用，絕不出現在回傳給前端的 JSON 回應中。

### 2. 內部 `error_code` 與客戶端人話訊息對照表

| `error_code` | HTTP | 客戶端 `message` | 觸發情境說明 |
| :--- | :--- | :--- | :--- |
| `request.bad_json` | `400` | 請求不是合法的 JSON | Content-Type 非 application/json 或語法破損 |
| `request.missing_field` | `400` | 缺少必填欄位 | 必填欄位為 null 或未提供 |
| `request.bad_value` | `400` | 欄位的值不合法 | 金額小於等於0、匯率不大於0、日期格式不對、種類不在白名單 |
| `conflict.unique_name` | `400` | 這個名稱已經有了 | 帳戶名稱、入帳分類名稱或花費分類名稱重複 |
| `conflict.unique_invoice` | `400` | 這張發票號碼已經登錄過 | 發票號碼重複登錄 |
| `conflict.unique_symbol` | `400` | 這個市場已經有這個代號 | 同一市場內已有相同證券代號 |
| `conflict.foreign_key` | `400` | 找不到要對應的資料 | 參照了不存在的帳戶、分類、發票或標的 |
| `rule.empty_text` | `400` | 來源與備註至少填一個（入帳）<br>商家與備註至少填一個（花費） | 入帳之來源與備註皆空，或花費之商家與備註皆空 |
| `rule.same_account` | `400` | 轉出與轉入不能是同一個帳戶 | 移轉之來源帳戶與目的帳戶相同 |
| `rule.sell_exceeds_holding` | `400` | 賣出的數量超過目前持有 | 賣出股數大於當前累積持有股數 |
| `rule.prize_already_posted` | `400` | 這張發票已經入過帳 | 發票已領獎或已有入帳關聯 |
| `rule.void_with_income` | `400` | 這筆交易已經有入帳，不能作廢 | 交易已有關聯入帳紀錄，禁止作廢 |
| `not_found` | `404` | 找不到這一筆 | 指定之 ID 於資料庫查無紀錄 |
| `server.database` | `500` | 資料庫暫時連不上 | 連線逾時、資料庫斷線或認證失敗 |
| `server.unhandled` | `500` | 暫時無法完成，請稍後再試 | 未捕獲之程式內部例外 |

### 3. 日誌輸出範例（`conflict.unique_name`）
當用戶端送出重複名稱（例如重複新增 `{"name": "現金錢包", ...}`）時，伺服器日誌產生的內部 JSON 物件如下：
```json
{
  "time": "2026-11-13T04:15:30Z",
  "request_id": "req-9b8a7c6d-5e4f-3a2b",
  "method": "POST",
  "path": "/api/accounts",
  "http_code": 400,
  "error_code": "conflict.unique_name",
  "exception_type": "IntegrityError",
  "sqlstate": "23505",
  "constraint_name": "uq_accounts_name",
  "table_name": "accounts",
  "detail": "Key (name)=(現金錢包) already exists."
}
```

## 六、與現況的差異 (Differences from Current Implementation)

本文件依據步驟 14 之規格定義。依約束條件「不修改現有程式」，現行 `./ledger-api/app.py` 實作與步驟 14 約定有以下幾點差異，供後續串接與測試對照參考：

1. **帳戶餘額端點（`GET /api/accounts/<id>/balance`）**：
   - **步驟 14 約定**：`data` 僅包含 4 個鍵名：`account_id`、`currency`、`currency_balance`、`twd_balance`。
   - **現況實作**：`data` 包含 `account_id`、`name`、`currency`、`opening_balance`、`balance`、`balance_twd`、`original_balance`、`twd_balance`。原幣別餘額鍵名在現況中為 `balance` / `original_balance`，尚無 `currency_balance`。

2. **投資持有端點（`GET /api/instruments/<id>/holding`）**：
   - **步驟 14 約定**：`data` 僅約定 4 個鍵名：`instrument_id`、`quantity`、`average_cost`、`currency`。
   - **現況實作**：`data` 除上述 4 個鍵名外，額外帶有便利性輔助欄位 `symbol`、`name` 與 `total_cost`。

3. **錯誤訊息（`message`）文字細緻度**：
   - **步驟 14 約定**：各類錯誤收斂至固定的人話字典表（例如 `request.missing_field` 一律回傳 `"缺少必填欄位"`；`conflict.unique_name` 一律回傳 `"這個名稱已經有了"`；`not_found` 一律回傳 `"找不到這一筆"`）。
   - **現況實作**：現行 API 在多個端點採用了個別針對性的提示文字（例如 `"必填欄位缺失: name"`、`"帳戶名稱已存在，請使用其他名稱"`、`"找不到該發票"`、`"找不到該投資標的"`、`"找不到該筆交易"`）。

4. **伺服器日誌架構**：
   - **步驟 14 約定**：伺服器端發生錯誤時應記錄包含 `request_id`、`error_code`、`sqlstate` 等鍵的標準結構化 JSON 物件。
   - **現況實作**：現行 API 使用 Flask 內建 logger 紀錄格式化文字字串與 Exception 堆疊追蹤（如 `app.logger.error(...)`），尚未全面轉換為注入 `error_code` 的 JSON 日誌結構。
