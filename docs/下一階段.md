# 個人記帳本 API 與前端實作落差掃描規格書（下一階段規劃）

本文件由前端程式開發設計師視角出發，全面盤點後端 RESTful API（`app.py`、`docs/交換格式.md`、`docs/前端串接.md`）與當前手機版畫面（`ledger-web/index.html`、`styles.css`、`app.js`）之間的實作現況，進行精確的技術落差掃描，作為下一階段迭代之規格依據。

---

## 一、已接上 (Connected)

本節列出目前後端 API 已經提供，且前端手機畫面已完整介接並具備互動功能的端點：

| HTTP 方法 | 端點路徑 | 成功時 `data` 重點欄位 | 畫面用在哪一頁與使用情境 |
| :---: | :--- | :--- | :--- |
| `GET` | `/api/health` | `status`, `time` | **連線設定頁**：App 啟動冷開機或使用者輸入伺服器網址時，驗證後端連線健康狀態。 |
| `GET` | `/api/summary` | `month`, `income_twd`, `expense_twd` | **首頁**：載入本月生活現金流卡片，顯示本月入帳、本月花費與淨儲蓄。 |
| `GET` | `/api/accounts` | 陣列：`id`, `name`, `kind`, `currency`, `opening_balance` 等 | **首頁**（帳戶資產卡片列表）與**記帳頁**（扣款帳戶與存入帳戶下拉選單）。 |
| `GET` | `/api/accounts/<int:account_id>/balance` | `account_id`, `currency`, `currency_balance`, `twd_balance` | **首頁**：依帳戶 ID 平行即時計算並呈現台幣餘額與原幣餘額。 |
| `POST` | `/api/accounts` | 完整帳戶物件（含主鍵 `id`） | **首頁**：當系統查無帳戶時，於同一頁內嵌表單快速建立初始「現金錢包」帳戶。 |
| `GET` | `/api/expense-categories` | 陣列：`id`, `name`, `description` | **記帳頁**：動態載入花費分類下拉選單。 |
| `POST` | `/api/expense-categories` | 新增之花費分類物件 | **記帳頁**：清單為空或點擊「+ 新增分類」時，內嵌表單快速建立花費分類。 |
| `GET` | `/api/income-categories` | 陣列：`id`, `name`, `description` | **記帳頁**：動態載入入帳分類下拉選單。 |
| `POST` | `/api/income-categories` | 新增之入帳分類物件 | **記帳頁**：清單為空或點擊「+ 新增分類」時，內嵌表單快速建立入帳分類。 |
| `POST` | `/api/expenses` | 新增之花費列物件（含 `id`, `spent_on`, `amount` 等） | **記帳頁**：送出日常消費支出紀錄，成功後將新列即時插入本月清單最上方。 |
| `POST` | `/api/incomes` | 新增之入帳列物件（含 `id`, `received_on`, `amount` 等） | **記帳頁**：送出薪資所得入帳紀錄，成功後將新列即時插入本月清單最上方。 |
| `GET` | `/api/expenses` (帶查詢參數 `date_from`, `date_to`) | 花費物件陣列 | **記帳頁**：載入當月份所有已發生的日常花費明細。 |
| `GET` | `/api/incomes` (帶查詢參數 `date_from`, `date_to`) | 入帳物件陣列 | **記帳頁**：載入當月份所有已發生的收入明細，並與花費合併依時間倒序呈現於「本月收支清單」。 |
| `GET` | `/api/instruments` | 標的物件陣列（`id`, `market`, `symbol`, `name`, `currency`） | **投資頁**：載入投資標的清單，前端過濾 `market === 'tw_stock'` 台股標的展示。 |
| `GET` | `/api/instruments/<int:instrument_id>/holding` | `instrument_id`, `quantity`, `average_cost`, `currency` | **投資頁**：依標的 ID 查詢當前歷史交易重播計算之累積持有股數 `quantity`。 |
| `GET` | `/api/invoices` | 發票物件陣列（`id`, `number`, `issued_on`, `amount`, `kind`, `prize_status`） | **發票頁**：載入統一發票清單（只讀模式，顯示號碼、開立日、金額與中獎標籤）。 |

## 三、畫面有、API 沒有 (UI Implemented, API Missing)

本節列出前端手機畫面依照使用者直覺或前置指示設計了互動行為，但後端 `app.py` 中實際上**並不存在該端點**，導致客戶端呼叫時取得 HTTP 404 之項目：

1. **取得單一標的最新報價**
   - **畫面行為**：在「投資頁」渲染每一檔台股標的卡片時，`app.js` 會呼叫 `GET /api/instruments/<id>/quote`，期望取得該標的最新成交價或收盤價以顯示於右上角。
   - **缺的端點與現況**：後端 `app.py` 與 `docs/交換格式.md` 中**完全未實作該端點**。目前前端已做好優雅降級容錯，當取得 404 時於畫面上顯示「還沒有報價」。
2. **手動觸發向證交所同步台股報價**
   - **畫面行為**：在「投資頁」頂部設有「抓取台股報價」按鈕，使用者點擊時會向後端發送 `POST /api/tw-stock-quotes/fetch`，並期望自回應取得 `data.missing` 與 `data.skipped` 數量，轉化為人話回饋使用者。
   - **缺的端點與現況**：後端 `app.py` **完全未定義該端點**，呼叫時回傳 `404 Not Found`（訊息：「找不到這一筆」），前端依規格捕獲並以 Toast 提示該訊息。

## 四、路徑、欄位或錯誤句子對不上的地方 (Mismatches & Inconsistencies)

本節列出在既有已串接的端點中，API 現行回傳結構、規格書定義與畫面預期之間存在的細微落差：

1. **帳戶即時餘額的原幣餘額鍵名差異**
   - **端點**：`GET /api/accounts/<int:account_id>/balance`
   - **API 現況**：在 `app.py` 中，回傳的 `data` 鍵名為 `account_id`、`name`、`currency`、`opening_balance`、`balance`、`balance_twd`、`original_balance`、`twd_balance`。原幣餘額使用 `original_balance` 與 `balance`，尚未提供規格書約定之 `currency_balance`。
   - **畫面現況**：前端 `app.js` 為了相容規格書，讀取了 `balData.currency_balance`，導致外幣帳戶在卡片上未顯示原幣金額，僅顯示了換算後的 `twd_balance`。
2. **投資持有股數端點的回傳欄位豐富度**
   - **端點**：`GET /api/instruments/<int:instrument_id>/holding`
   - **API 現況**：後端回傳包含 `instrument_id`、`symbol`、`name`、`currency`、`quantity`、`average_cost`、`total_cost`，欄位較交換格式原本約定的 4 個鍵名多出 `total_cost` 等實用資訊。
   - **畫面現況**：前端目前僅取用 `quantity` 呈現持有股數，未將後端已算妥的 `average_cost`（平均成本）與 `total_cost`（總投入成本）呈現在卡片上。
3. **錯誤訊息（`message`）文字精確度與規格書固定句子的分歧**
   - **端點**：全系統錯誤處理
   - **API 現況**：`docs/交換格式.md` 約定錯誤訊息收斂至字典固定人話（例如 `request.missing_field` 固定為 `"缺少必填欄位"`；`not_found` 固定為 `"找不到這一筆"`）；但 `app.py` 實作中多處採用針對性字串（例如 `"必填欄位缺失: name"`、`"找不到該投資標的"`、`"找不到該發票"`）。
   - **畫面現況**：前端嚴格遵守「失敗時畫面只顯示 `message`」，直接將後端回傳之字串透過 Toast 提示使用者，因此呈現的是動態欄位錯誤訊息。
4. **花費記帳缺少掛載統一發票欄位**
   - **端點**：`POST /api/expenses`
   - **API 現況**：後端支援 `invoice_id`（選填，整數），支援一筆發票對應多筆消費花費。
   - **畫面現況**：前端記帳表單目前僅收集了日期、金額、扣款帳戶、分類、商家、備註與扣款日，未提供發票下拉選單供關聯 `invoice_id`。
5. **月度生活現金流合計缺少歷史月份切換介面**
   - **端點**：`GET /api/summary?month=YYYY-MM`
   - **API 現況**：後端支援帶入任意合法之 `month` 查詢參數（如 `2026-08`）。
   - **畫面現況**：前端 `app.js` 目前寫死帶入當前執行時的西元年月份 `getCurrentMonthKey()`，畫面上無「前一月 / 後一月」切換按鈕，限制了該 API 的發揮空間。

## 五、下一階段建議先做的項目 (Recommended Next Steps)

嚴格依據上述掃描出的「落差」進行規劃，聚焦於現有後端 API 已備妥但前端尚未開放操作的高價值功能：

### 項目一：日常記帳收支明細的單筆編輯與更正 (PATCH Incomes & Expenses)
- **目的**：滿足使用者記錯金額、分類或商家備註時的修改需求，落實個人記帳最核心的更正機制。
- **會用到的端點**：
  - `GET /api/incomes/<int:income_id>`、`PATCH /api/incomes/<int:income_id>`
  - `GET /api/expenses/<int:expense_id>`、`PATCH /api/expenses/<int:expense_id>`
- **不改哪些既有行為**：
  - 不更動現有「新增花費」與「新增入帳」表單的送出機制。
  - 不變動本月收支清單在新增後即時將新列插入最上方的現有渲染機制。
  - 不變動後端商業約束（如入帳來源與備註不可皆空、花費商家與備註不可皆空）。

### 項目二：首頁生活現金流跨月份切換查看 (Summary Month Selector)
- **目的**：讓使用者可以在首頁自由切換查看上個月或指定歷史月份的收支儀表板與淨儲蓄累積。
- **會用到的端點**：
  - `GET /api/summary?month=YYYY-MM`
  - `GET /api/incomes?date_from=...&date_to=...`
  - `GET /api/expenses?date_from=...&date_to=...`
- **不改哪些既有行為**：
  - 不變動預設進入首頁時自動載入「當月」收支的現有行為。
  - 不變動帳戶餘額的即時計算方式（帳戶餘額始終代表當前最新真實資產）。

### 項目三：發票一鍵自動對獎與中獎領獎轉入帳 (Draw Checking & Prize Claiming)
- **目的**：使發票專區不再是純唯讀展示，讓使用者能一鍵自動對獎，並將中獎獎金無縫轉入指定之活存或現金帳戶。
- **會用到的端點**：
  - `GET /api/draw-periods`（讀取當前開獎期別與中獎號碼）
  - `POST /api/draw-periods/<int:period_id>/check`（執行發票號碼自動對獎）
  - `POST /api/invoices/<int:invoice_id>/prize-income`（領獎入帳，自動建立入帳紀錄並將發票改為 `claimed`）
- **不改哪些既有行為**：
  - 不變動既有發票清單的號碼、開立日、金額與狀態標籤外觀。
  - 不變動發票狀態為 `void`（作廢）時禁止對獎與領獎的既有防護機制。

### 項目四：帳戶資金移轉功能（Transfers Tab）
- **目的**：提供銀行提款放皮夾、帳戶間轉帳與繳納信用卡費的專屬表單，避免使用者將內部轉帳誤記為消費支出而造成收支虛增。
- **會用到的端點**：
  - `POST /api/transfers`
  - `GET /api/transfers`
- **不改哪些既有行為**：
  - 不變動既有記帳頁中的花費表單與入帳表單；僅將頂部切換開關由雙分頁擴充為三分頁（[花費] / [入帳] / [移轉]）。
  - 不變動轉出帳戶與轉入帳戶不得相同（`rule.same_account`）之商業規則。

### 項目五：投資交易買賣記錄與交易作廢 (Trades Management & Void)
- **目的**：在「投資頁」提供真實的股票買進（`buy`）與賣出（`sell`）表記錄，使標的持股數由真實交易鏈累積驅動，並支援記錯時的交易作廢。
- **會用到的端點**：
  - `POST /api/trades`
  - `GET /api/trades`
  - `POST /api/trades/<int:trade_id>/void`
- **不改哪些既有行為**：
  - 不變動目前僅篩選台股 `tw_stock` 標的之卡片呈現。
  - 不發明亦不做股票市值合計（恪遵約束）。
  - 不變動賣出股數不得大於持有股數（`rule.sell_exceeds_holding`）之防呆驗證。
